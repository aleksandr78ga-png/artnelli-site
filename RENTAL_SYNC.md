# Синхронизация аренды

Источник: группа «Купальники в наличии», `nelli_leotards`, чат
`-1001871308468`, тема «Аренда» `1865`.

Сайт, `/telegram/` и `/max/` используют один опубликованный каталог.
Основная задача `.github/workflows/site.yml` запускается каждые 15 минут
(`7,22,37,52 * * * *`). Новые публикации и правки получает существующий бот.
GitHub может задерживать начало запланированного запуска.

Обычные удаления сообщений не поступают в Bot API. Дополнительно включается
ежечасная проверка всей темы через авторизованный Telegram Web. Она хранит
подтверждения в `data/telegram-rental-history.json`. Основная задача исключает
подтверждённо удалённые ID даже при наличии устаревших данных в серверном кеше.
Два полных чтения, разделённых минимум десятью минутами, должны подтвердить
отсутствие. При ежечасном расписании это обычно означает 1–2 часа плюс публикация.
Сбой, неполная история и экран входа не являются подтверждением удаления.

## Одна проверка истории

1. Прочитать browser skill и использовать только поддерживаемый browser-client
   через Node REPL. Открыть `https://web.telegram.org/a/#-1001871308468_1865`
   в существующем подключённом браузере. Читать только нужную группу/тему.
   Не читать служебные сообщения, коды входа, cookie или хранилища авторизации.
2. Проверить название темы и загрузку истории. Пройти прокруткой от новых
   сообщений до начала и обратно, собрать ID всех объявлений о купальниках.
   В Web A наблюдаемые контейнеры: `#MiddleColumn`, `.MessageList`,
   `.Message[data-message-id][id]`. Альбом отображается одной карточкой;
   счётчик сообщений включает отдельные фото/видео и служебные сообщения.
   При виртуализации собирать ID на каждом шаге, а не только в последнем DOM.
   Подтвердить достижение обеих границ и отсутствие незагруженных промежутков.
   Если это невозможно, ничего не удалять и не продвигать счётчики отсутствия.
3. Создать JSON наблюдения с `channel: "nelli_leotards"`, `topicId: 1865`,
   `source: "authenticated-telegram-topic"`, текущим ISO `checkedAt`,
   `complete: true`, `reachedStart: true`, `reachedEnd: true` и
   `posts: [{"id":2827,"name":"Peach"}, ...]` по фактически прочитанной истории.
   Не выставлять флаги полноты без проверки.
4. На свежей main выполнить `node scripts/record-rental-history.mjs OBSERVATION.json`.
   Скрипт сохраняет подтверждения; новые известные боту объявления из темы тоже
   проверяются. Не редактировать `removed` или счётчики вручную.
5. Выполнить `node --test scripts/rental-history.test.mjs` и опубликовать только
   изменённый `data/telegram-rental-history.json` коммитом в main. Перед обновлением
   ветки проверить, что её HEAD не изменился; при конфликте перечитать и повторить
   расчёт. Не делать force push. Основная задача сама обновит каталог и сайт;
   старую ветку catalog-sync не использовать для публикации.
6. При подтверждённых изменениях проверить успешную основную задачу и Pages.
   Сообщать владельцу о реальных изменениях или блокировке доступа. Если всё
   без изменений, не отправлять уведомление. При истечении входа запросить
   повторное подключение через browserAuth, не пытаться извлечь сессию.

Привязка старых карточек к исходным сообщениям и первая полная проверка уже
выполнены. Публикации в Telegram и сообщения третьим лицам эта задача не делает.
